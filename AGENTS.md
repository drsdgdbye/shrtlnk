# Общие правила разработки на Go

## Обязательные проверки

Перед завершением задачи код должен проходить:

- `gofmt -l .` — список неотформатированных файлов пуст;
- `go vet ./...` — без замечаний;
- `go build ./...` — все пакеты собираются;
- `go test ./...` — все тесты проходят;
- `go test -race ./...` — обязателен для кода с конкурентностью;
- `go mod tidy` — при любом изменении зависимостей.

Если в проекте настроены `golangci-lint`, `staticcheck` или `govulncheck`, прогнать и их. Задача не считается завершённой, пока проверка падает или не объяснено, почему её нельзя выполнить.

## Стиль и идиоматика

- Формат определяет `gofmt`; отклоняться от него не нужно. Импорты группируются: сначала стандартная библиотека, затем внешние пакеты. Переименование импорта — только для разрешения конфликта.
- Имена — `MixedCaps`, без `snake_case` и `SCREAMING_CASE`. Аббревиатуры сохраняют регистр целиком: `URL`, `ID`, `HTTP` — `ServeHTTP`, `appID`.
- Длина имени растёт вместе с областью видимости: для короткой области годятся `i`, `r`, `c`; для экспортируемого API — полное описательное имя.
- Получатель метода (`receiver`) — одна-две буквы, одинаково во всех методах типа. `this`, `self`, `me` не используются.
- Пакеты короткие и названы по предметной области. `util`, `common`, `misc`, `helpers`, `types` — плохие имена. Имя типа не повторяет имя пакета: `config.Config`, а не `config.ConfigFile`.
- Геттеры не получают префикс `Get`: `JobName()`, а не `GetJobName()`.
- Интерфейс объявляется в пакете-потребителе и только тогда, когда он реально нужен (второй потребитель, подстановка в тесте). Реализующий пакет возвращает конкретный тип.
- Интерфейсы не создаются заранее «на будущее»: без примера использования невозможно понять, какие методы нужны.
- Обобщение, в том числе дженерики, вводится под конкретную задачу, а не ради абстракции.

## Ошибки и контекст

- Ошибку нельзя отбрасывать через `_`: её обрабатывают, возвращают или логируют.
- Ошибка оборачивается с добавлением контекста через `%w`; проверка — через `errors.Is`/`errors.As`. Сравнение ошибок по тексту запрещено.

```go
cfg, err := loadConfig(path)
if err != nil {
    return fmt.Errorf("загрузка конфига %q: %w", path, err)
}
```

- Текст ошибки — со строчной буквы и без точки в конце: `errors.New("файл не найден")`.
- `panic` — только для программных ошибок и недостижимых состояний, не для обычной обработки. Библиотека возвращает ошибку вызывающему.
- `context.Context` — первый параметр функции, а не поле структуры. Контекст передаётся по всей цепочке вызовов.
- Внешние вызовы (HTTP, БД, подпроцессы) получают таймаут или дедлайн.

```go
func (c *Client) Fetch(ctx context.Context, url string) (*Response, error) {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    // ...
}
```

- `errors.Join` используется, когда нужно вернуть несколько независимых ошибок одновременно.

## Конкурентность и ресурсы

- У каждой горутины есть понятное условие завершения. Запуск «в никуда» приводит к утечке.
- Синхронная функция предпочтительнее асинхронной: конкурентность при необходимости добавляет вызывающий.
- Канал принадлежит тому, кто его создал: только создатель пишет в канал и закрывает его.
- Для групп однотипных горутин применяются `errgroup` или `sync.WaitGroup`; общий доступ к памяти защищается мьютексом или каналом.
- Файлы, тела HTTP-ответов и прочие ресурсы закрываются через `defer` сразу после получения.
- Разделяемое состояние либо неизменно, либо защищено. Глобальные изменяемые переменные не используются.

## Структура проекта

- Точки входа — `cmd/<binary>/`; при единственном бинарнике допустим `main.go` в корне.
- Приватный код — в `internal/`; каталог `pkg/` без внешних потребителей не нужен.
- Код группируется по предметной области, а не по слоям: `order`, `payment`, `storage`, а не россыпь `models`, `handlers`, `services`.
- Связанные типы живут в одном пакете. Если два пакета почти всегда импортируются вместе, вероятно, это один пакет.
- Циклические зависимости между пакетами недопустимы; зависимости направлены в сторону предметной области.
- `main` только собирает зависимости и запускает приложение. Логика находится в `internal/`.

## Тестирование

- Новая и изменённая логика покрывается тестами; `go test ./...` проходит.
- Тесты лежат рядом с кодом в файлах `_test.go`; внешние тесты — в пакете `<pkg>_test`.
- Много однотипных случаев — табличный тест с `t.Run`; разная логика проверки — разные функции.

```go
func TestParse(t *testing.T) {
    tests := []struct {
        name string
        in   string
        want int
    }{
        {name: "число", in: "42", want: 42},
        {name: "пустая строка", in: "", want: 0},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Parse(tt.in)
            if err != nil {
                t.Fatalf("Parse(%q) error: %v", tt.in, err)
            }
            if got != tt.want {
                t.Errorf("Parse(%q) = %d, want %d", tt.in, got, tt.want)
            }
        })
    }
}
```

- Assert-библиотеки не используются: проверка пишется на самом Go. Структуры сравниваются целиком через `cmp.Diff`/`cmp.Equal`, а не по полям.
- Вспомогательные функции помечаются `t.Helper()`; временные файлы создаются через `t.TempDir()`, переменные окружения — через `t.Setenv`, очистка — через `t.Cleanup`.
- `t.Error` предпочтительнее `t.Fatal`: тест продолжается и сообщает обо всех расхождениях. `t.Fatal` уместен, только когда продолжение невозможно.
- Проверяется поведение, а не реализация. Тип ошибки проверяется через `errors.Is`/`errors.As`, а не по строке сообщения.
- Моки пишутся руками и реализуют интерфейс потребителя. Фреймворки и кодогенерация — только при весомой необходимости.
- Обязательны негативные и граничные сценарии: пустой ввод, отказ зависимости, отмена контекста, превышение лимитов.
- Для парсеров и разбора внешних данных пишутся fuzz-тесты; для публичного API — `Example`-функции.
- Тест не зависит от сети, системного времени, порядка выполнения и общего состояния.

## Зависимости

- Приоритет — стандартной библиотеке. Каждая новая зависимость обосновывается.
- `go.mod` и `go.sum` поддерживаются в актуальном состоянии, версии фиксируются.
- Перед добавлением модуля проверяются его поддержка, лицензия, размер и репутация.
- `govulncheck ./...` — обязательная проверка известных уязвимостей.
- Библиотеки минимизируют число зависимостей: каждое лишнее требование ложится на потребителей.

## Надёжность и безопасность

- Криптографическая случайность — только `crypto/rand`. `math/rand` для ключей и токенов не подходит.
- Секреты берутся из окружения или секрет-хранилища. Они не попадают в репозиторий, логи и тексты ошибок.
- `http.Server` и `http.Client` настраиваются с таймаутами; размер тела ответа ограничивается, тело закрывается.
- SQL-запросы только параметризованные; подстановка значений конкатенацией запрещена.
- Данные на границе системы (запрос, файл, сообщение) валидируются до использования.
- Завершение приложения — по сигналу через `signal.NotifyContext`, с graceful shutdown и таймаутом.

## Сборка и CI

- Сборка воспроизводима: версия Go берётся из `go.mod`, флаги компиляции фиксированы.
- Контейнеры собираются multi-stage; применяются `CGO_ENABLED=0`, статический бинарник, финальный образ без компилятора и исходников. Процесс запускается не от root.
- В CI обязательны форматирование, `go vet`, линтер, тесты (включая `-race`), сборка и `govulncheck`. Красный CI блокирует merge.
- Секреты в CI передаются через секреты репозитория, а не текстом в workflow.

## Документация и комментарии

- Все экспортируемые сущности имеют godoc-комментарий, начинающийся с имени сущности: `// Request описывает...`.
- Комментарий объясняет «почему» и неочевидные ограничения, а не пересказывает код.
- Пакет получает package-комментарий; при большом объёме документации выделяется `doc.go`.
- `TODO` и `FIXME` содержат суть и ссылку на задачу, а не только пометку.

## Язык текстов

- Документация, комментарии, описания задач и MR, рабочая переписка — на русском.
- Идентификаторы в коде (типы, функции, переменные) — на английском.
- Пользовательские и эксплуатационные тексты — на языке, которого требует контракт продукта.
- Язык сообщений коммитов определяется конвенцией проекта.

## Работа с GitHub

- Все операции с GitHub выполняются через CLI `gh`: pull request, issues, релизы, GitHub Actions, просмотр репозитория. Веб-интерфейс и `curl` с токенами не используются.
- Перед началом работы проверяется авторизация: `gh auth status`. Если её нет — `gh auth login`.
- Статус проверок и логов workflow смотрятся через `gh pr checks` и `gh run list`/`gh run view`.
- В автоматизированных сценариях команды запускаются с явными флагами (`gh pr create --title ... --body ... --base ...`), без интерактивных запросов.
- Токены и секреты не передаются аргументами команд и не попадают в историю shell.

## Коммиты и MR

- Коммит атомарен: одно смысловое изменение. Код и тесты к нему — в одном коммите.
- Сообщение императивное, первая строка до 72 символов, детали — в теле.
- В репозиторий не попадают секреты, бинарники, артефакты сборки и временные файлы.
- Описание MR отвечает на вопросы: что изменено, зачем, как проверено.
- Изменение не мержится с падающими проверками.
